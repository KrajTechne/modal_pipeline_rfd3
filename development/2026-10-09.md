## One checkout per kit, decided by a one-minute experiment

The plan was one `~/ubm` holding both kits, isolated per build with
`from_dockerfile(ignore=[...])`. Tested rather than assumed, and on a throwaway
two-line image rather than on ESMFold2's, whose rebuild costs ~38 minutes:

```
plain       -> im-KJdhHAifLYHCLHbXetXCvK
with ignore -> im-zHmjutecvwWgmrbgr2WdUF
```

Identical contexts, `ignore` naming only paths that do not exist, and still two
distinct image ids. **Modal hashes the `ignore` spec itself**, not the
post-ignore file set. So consolidating would have cost a full ESMFold2 rebuild
merely to introduce the ignore, in exchange for 306 MB of saved disk with 24 GB
free.

Separate checkouts, then: `~/ubm` for ESMFold2, `~/ubm_af3` for af3_jax. The
experiment cost about a minute and saved finding out the expensive way -- which
is the lesson worth keeping from yesterday's six build attempts.

## The af3_jax kit, first attempt

**435 s to build**, against ESMFold2's 2615 across six attempts. The difference
is structural, not luck: this Dockerfile compiles only the stock alphafold3
wheel, where ESMFold2 compiles flash-attn and TransformerEngine from source.

```
stock wheel: compiling with 8 parallel jobs (17 cores here)
Successfully built alphafold3_open-3.1.4-cp312-cp312-linux_x86_64.whl
Built image in 435.15s   (24 steps)
```

Both of yesterday's ESMFold2 traps were applied before they could bite:
`core.autocrlf=false` on the clone, and an empty
`_jitcache/af3_jax-empty-jit.tar`, because this Dockerfile has the *identical*
optional-COPY glob at line 101 that Modal refuses. `BUILD_JOBS` capped at 8 for
the same reason as ESMFold2, though with one light wheel it was probably
unnecessary -- it costs nothing and the OOM it prevents is machine-dependent.

The digest matches the one `install` reported, so the conversion round-trips.

### warm, and a mistake worth recording

First attempt returned `WARM PARTIAL ... executables=0 predictions=0` with
every lever "not traced", and `cache_sha256=e3b0c442...` -- the digest of empty
input. The cause was mine: `warm` takes `--input_dir`, and I passed the
*parent* of the inputs directory, which holds no JSONs.

Two things to notice. The kit logged `rc=0` internally while `run.sh` exited
**3**, correctly refusing to claim success when no lever was served -- so
reading only the inner `rc` would have called this a pass. And the empty-input
digest is a cheap tell that nothing was traced.

With the right directory: `WARM PASS`, 25 predictions, 409 kernels, 2.3 MB,
115 s.

## Native AF3 weights: approval was not the blocker

The user has approval for native AF3 weights, which closed the licensing
question. It does not close the engineering one.

`install` fetches `of3-p2-155k.pt` -- an **OpenFold3** checkpoint -- and
converts it:

```
FETCH    variant=p2 path=/weights/af3/checkpoints/of3-p2-155k.pt sha256_ok=True
Convert  4936 tensors -> 329 scopes, 368,388,764 elements
Saving   /weights/af3/p2/of3_ported_weights.bin.zst  (1369 MB)
CONVERT  status=PASS matches_pin=True
```

Three things then stack up against a config flip:

1. `VARIANTS = ("p2",)` -- the only variant the kit knows, and required on
   `pred`, `check` and `warm`.
2. `PARAMS_FILE = "of3_ported_weights.bin.zst"` -- a caller's own weights
   directory *is* accepted via `--model_dir` ("always accepted, digested",
   reported **NOT PINNED**), but it must hold that file under that name.
3. The only converter shipped is `convert_of3_weights.py`, an OpenFold3
   converter. Whether it can read DeepMind's parameters is unverified, and the
   tensor layouts differ.

So `weights: af3_native` is a weights-conversion project, not a setting. Worth
saying plainly: cross-validation on OpenFold3 weights is still a genuinely
independent model from ESMFold2, so the stage's purpose is served either way --
it simply is not "AF3" in the strict sense.

## AF3's seeds: the plan had this wrong, twice

The fold-input schema turned out to carry its own seeds:

```json
{"dialect": ..., "version": ..., "name": ...,
 "modelSeeds": [1, 2, 3, 4, 5],
 "sequences": [{"protein": {"id": "A", "sequence": "...",
                            "unpairedMsa": "", "pairedMsa": "",
                            "templates": []}}]}
```

The plan recorded that "the AF3 fork takes `--num_seeds N` and *generates* the
seeds, so the ones used are only readable from its output JSON", and
`MODEL_CAPABILITIES` encoded that as `seed_style: COUNT`. Both wrong:

* **`--num_seeds` is optional.** `run_alphafold.py:414-424`: *"If not set,
  AlphaFold 3 will use the seeds as provided in the input JSON."*
* **Even when set, the seeds are not random.** `folding_input.py:1514` builds
  `range(base, base + N)` -- which is exactly what `seed_sequence(base, N)`
  already computes. A test now pins that equivalence.

So af3_jax is `seed_style: LIST`, and cross-validation's five seeds should be
passed explicitly as `modelSeeds`. That matters more here than anywhere else:
CV exists to be compared against, and seeds we chose are seeds we can re-run.

Also from that schema, for when the CV input is assembled: MSAs are **inline
strings in camelCase** (`unpairedMsa` / `pairedMsa`), not file paths as in
ESMFold2 -- and `""` is the *suppression* value, since an empty string counts as
set and `fill_missing_msas` skips it. The kit's own example ships with both
empty, i.e. fetching deliberately off.

## Next

**Assemble the CV input and write the af3 refold wrapper.** The pieces are now
known: a directory of fold-input JSONs, explicit `modelSeeds`, inline
`unpairedMsa`/`pairedMsa` per chain, `--variant p2`, `--input_dir` /
`--output_dir`.

The one piece still missing is **paired alignments**, which the MSA cache
deliberately does not build -- unpaired is a property of one sequence and so
cacheable, paired is a property of the set of chains queried together. af3_jax
is the only model with `msa_paired=True`, so this is where that work lands, and
where the user's decision that binder sequences may appear in a paired query
applies.

One campaign-specific shortcut worth exploiting: because the binder is always
suppressed, the pairing context is exactly the target set, which does not change
across a campaign -- so the targets' paired MSA could be computed once rather
than per prediction.

Carried forward: the apo/holo gates (`threshold_rmsd_apo_holo`,
`threshold_ipTM`) now have data to act on, and boltz2's capability row remains
the least verified.
