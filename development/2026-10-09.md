## One checkout per kit, decided by a one-minute experiment

The plan was one `~/ubm` holding both kits, isolated per build with
`from_dockerfile(ignore=[...])`. Tested rather than assumed, and on a throwaway
two-line image rather than on ESMFold2's, whose rebuild costs ~38 minutes:

```
plain       -> im-KJdhHAifLYHCLHbXetXCvK
with ignore -> im-zHmjutecvwWgmrbgr2WdUF
```

Identical contexts, `ignore` naming only paths that do not exist, and still two
distinct image ids. **Modal hashes the `ignore` spec itself**, not the
post-ignore file set. So consolidating would have cost a full ESMFold2 rebuild
merely to introduce the ignore, in exchange for 306 MB of saved disk with 24 GB
free.

Separate checkouts, then: `~/ubm` for ESMFold2, `~/ubm_af3` for af3_jax. The
experiment cost about a minute and saved finding out the expensive way -- which
is the lesson worth keeping from yesterday's six build attempts.

**435 s to build**, against ESMFold2's 2615 across six attempts. The difference

wheel, where ESMFold2 compiles flash-attn and TransformerEngine from source.

Successfully built alphafold3_open-3.1.4-cp312-cp312-linux_x86_64.whl

Both of yesterday's ESMFold2 traps were applied before they could bite:
`core.autocrlf=false` on the clone, and an empty

ACTIVE mode=fast variant=p2 alphafold3=v3.1.4@bc32b22f

The digest matches the one `install` reported, so the conversion round-trips.

### warm, and a mistake worth recording

First attempt returned `WARM PARTIAL ... executables=0 predictions=0` with
every lever "not traced", and `cache_sha256=e3b0c442...` -- the digest of empty
input. The cause was mine: `warm` takes `--input_dir`, and I passed the
*parent* of the inputs directory, which holds no JSONs.

Two things to notice. The kit logged `rc=0` internally while `run.sh` exited
**3**, correctly refusing to claim success when no lever was served -- so
reading only the inner `rc` would have called this a pass. And the empty-input
digest is a cheap tell that nothing was traced.

With the right directory: `WARM PASS`, 25 predictions, 409 kernels, 2.3 MB,
115 s.

## Native AF3 weights: approval was not the blocker

The user has approval for native AF3 weights, which closed the licensing
question. It does not close the engineering one.

`install` fetches `of3-p2-155k.pt` -- an **OpenFold3** checkpoint -- and
converts it:

```
FETCH    variant=p2 path=/weights/af3/checkpoints/of3-p2-155k.pt sha256_ok=True
Convert  4936 tensors -> 329 scopes, 368,388,764 elements
Saving   /weights/af3/p2/of3_ported_weights.bin.zst  (1369 MB)
CONVERT  status=PASS matches_pin=True
```

Three things then stack up against a config flip:

1. `VARIANTS = ("p2",)` -- the only variant the kit knows, and required on
   `pred`, `check` and `warm`.
2. `PARAMS_FILE = "of3_ported_weights.bin.zst"` -- a caller's own weights
   directory *is* accepted via `--model_dir` ("always accepted, digested",
   reported **NOT PINNED**), but it must hold that file under that name.
3. The only converter shipped is `convert_of3_weights.py`, an OpenFold3
   converter. Whether it can read DeepMind's parameters is unverified, and the
   tensor layouts differ.

So `weights: af3_native` is a weights-conversion project, not a setting. Worth
saying plainly: cross-validation on OpenFold3 weights is still a genuinely
independent model from ESMFold2, so the stage's purpose is served either way --
it simply is not "AF3" in the strict sense.

## AF3's seeds: the plan had this wrong, twice

The fold-input schema turned out to carry its own seeds:

```json
{"dialect": ..., "version": ..., "name": ...,
 "modelSeeds": [1, 2, 3, 4, 5],
 "sequences": [{"protein": {"id": "A", "sequence": "...",
                            "unpairedMsa": "", "pairedMsa": "",
                            "templates": []}}]}
```

The plan recorded that "the AF3 fork takes `--num_seeds N` and *generates* the
seeds, so the ones used are only readable from its output JSON", and
`MODEL_CAPABILITIES` encoded that as `seed_style: COUNT`. Both wrong:

* **`--num_seeds` is optional.** `run_alphafold.py:414-424`: *"If not set,
  AlphaFold 3 will use the seeds as provided in the input JSON."*
* **Even when set, the seeds are not random.** `folding_input.py:1514` builds
  `range(base, base + N)` -- which is exactly what `seed_sequence(base, N)`
  already computes. A test now pins that equivalence.

So af3_jax is `seed_style: LIST`, and cross-validation's five seeds should be
passed explicitly as `modelSeeds`. That matters more here than anywhere else:
CV exists to be compared against, and seeds we chose are seeds we can re-run.

Also from that schema, for when the CV input is assembled: MSAs are **inline
strings in camelCase** (`unpairedMsa` / `pairedMsa`), not file paths as in
ESMFold2 -- and `""` is the *suppression* value, since an empty string counts as
set and `fill_missing_msas` skips it. The kit's own example ships with both
empty, i.e. fetching deliberately off.

## The kit refuses its own kernels, and the diagnosis took two tries

`pred` completes every prediction -- `predictions=10/10`, 37 output files with
`iptm`, `ptm`, `ranking_score`, `chain_pair_iptm` all present -- and still exits
**5 `kernels_refused`**, with 5 of 16 levers engaged. Under `fast`, under
`exact`, and under `off` identically, because the failing component sits below
the kit's own lever switch.

```
Tokamax autotune unavailable (RuntimeError: AttributeError:
  'jaxlib...ir.NameLoc' object has no attribute 'is_a_name')
```

**First guess, wrong:** a jax/jaxlib mismatch from the Dockerfile. Measured in
the running image instead of assumed: `jax`, `jaxlib` and `jax-cuda12-plugin`
are all 0.10.2, precisely as `requirements.lock` pins them.

**Second guess, also wrong, and the instructive one:** "jaxlib 0.10.2 dropped
the `is_a_*` accessors." It reads plausibly and it is false. The fork image runs
jaxlib **0.10.1**, and `[a for a in dir(ir.NameLoc) if "is_a" in a]` is empty
there too -- MLIR had already replaced that family with isinstance-style checks
before either version. What actually differs is that **tokamax 0.0.12 calls one
and 0.0.11 does not.**

The lesson is the same one the `ignore`-spec experiment taught earlier today:
the second environment is the control. One probe against a *working* stack
falsified a story that was internally consistent and fitted every observation
from the broken one.

Either way the verdict holds -- two versions the kit itself pinned, so unpinning
means fighting its own `check_pins` -- and the refused levers are performance
levers, not correctness.

## The fork, directly: one minute instead of 435 seconds

`model: af3_fork`, driving `sokrypton/alphafold3` through `run_alphafold.py`.
Prior art was the user's own Optimus repo, which already does this on Modal, so
this was mostly a matter of lifting a known-good recipe rather than discovering
one.

```
debian_slim(python_version="3.13")
  + jax[cuda12]==0.10.1, tokamax==0.0.11, dm-haiku, rdkit
  + the fork's published wheel (v3.1.5, cp313)
  + run_alphafold.py / convert_of3_weights.py, fetched at the wheel's tag
  + build_data
```

No Dockerfile, no sparse checkout, no CRLF workaround, no empty-tar workaround,
nothing compiled from source. The whole class of problem that cost six attempts
on ESMFold2 does not arise.

Two deliberate departures from Optimus, both because this is a campaign stage
rather than a one-off prediction:

* **Pins copied, not floated.** `jax 0.10.1` / `tokamax 0.0.11` are one minor
  version below the kit's broken pair on each. v3.1.7 exists and would drop the
  `build_data` step by bundling `components.cif`, but v3.1.5's notes say
  v3.1.4 -> v3.1.5 was "packaging only, no functional changes to inference" --
  nothing to gain yet, a working combination to lose.
* **Scripts pinned to the wheel's tag**, not `refs/heads/main`, so
  `run_alphafold.py` cannot drift away from the wheel it drives.

And one departure in the other direction: **weights on the volume**, where
Optimus bakes both sets into image layers. The repo already has a
`populate_*_weights` convention, and it means a weight swap costs no rebuild.

### Native AF3 weights turned out to be a config flip

This closes open question 4 in the plan, which only looked hard because of the
kit. `af3.bin.zst` loads into this fork as-is:

```
of3  (converted)  1369 MB   329 scopes, 368,388,764 elements
native            1020545840 B   sha256 74d0258616917cd1...
```

The kit made this look like a weights-conversion project because it hardcodes
`VARIANTS = ("p2",)` and the filename `of3_ported_weights.bin.zst`. The fork
names its weights directory outright via `--model_dir`, so both sets are just
directories. `weights: af3_native` selects it; the default stays `openfold3`, so
the non-commercial set never arrives by omission.

## The run, on real shards

Five seeds at one diffusion sample each, targets from our own MSA cache:

```
returncode  0
seconds     337.4       (379.7 cold -- the JIT cache on the volume saves ~42 s)
chains      protein:A  protein:B  protein:C  ligand:E
msa_depth   {'A': 1, 'B': 9105, 'C': 4481}
iptm 0.71   ptm 0.81   ranking_score 0.73   has_clash 0.0
```

`msa_depth` is the line worth having. "Skipping data pipeline..." in the log
proves only that AF3's genetic search was off -- targets folded from sequence
alone would still have produced a full set of interface numbers. AF3 echoes its
*resolved* input to `<name>_data.json`, so the depth it actually used is
readable rather than assumed: 1 for the binder (its stub, suppressed as
intended), 9105 and 4481 for the targets, read by absolute `unpairedMsaPath`.

Two runs in separate containers returned identical metrics, so `seed_style:
LIST` really does buy reproducibility here.

### A cost finding worth stating on its own

**`--num_diffusion_samples` defaults to 5.** Left alone, `num_seeds: 5` is
**25** predictions per sequence, not 5. The user set it to 1: seeds vary the
whole trajectory where samples vary only the diffusion branch, so for a
cross-check seeds are the better spend.

## What the MSA cache is worth, measured

The same sequence folded twice -- once from the cache, once with
`--use_msa_server` -- because the honest way to know what a cache costs is to
run without it. Safe to do: the binder keeps its stub in both modes, so only the
two public target sequences leave the container, and those are the same ones the
cache was built from.

| | cache | `--use_msa_server` |
|---|---|---|
| unpaired B / C | 9105 / 4481 | 9104 / 4480 |
| **paired** B / C | 0 (suppressed) | **1771 / 1771** |
| ipTM / pTM / ranking | 0.71 / 0.81 / 0.73 | 0.71 / 0.81 / 0.73 |
| chain_iptm | .28 / .58 / .61 / .47 | .29 / .58 / .62 / .47 |
| seconds | 337 | 343 |

**Pairing made no measurable difference on this complex.** 1771 paired rows per
target chain moved ipTM, pTM and ranking_score not at all, and two `chain_iptm`
entries by 0.01. One sequence on one target pair, so not a general claim -- but
it does retire paired alignments as a *blocker*, which is what the open question
was. The unpaired-only cache is sufficient to run the stage.

The unpaired depths also reproduce the server's to within exactly one record in
both chains -- a structural off-by-one in how the query sequence is counted, not
a different search.

And the mechanism is confirmed: the server run logged *"Querying ColabFold MSA
server for 2 unique protein sequence(s)"*, exactly the two targets. Only an
**absent** MSA field triggers a fetch; the binder's single-sequence stub kept it
out.

## Wiring it in

`CV_FUNCTIONS`, mirroring `REFOLD_FUNCTIONS` for the same reason -- a Modal
function's image is fixed at decoration time. Here the registry is guaranteed
useful rather than merely likely: `CampaignConfig` already rejects a campaign
whose two folding stages name the same model, so cross-validation always needs
a second image.

**The holo gate had to be built first.** Cross-validation selects on
`holo_pass`, and only `apo_pass` existed -- both holo thresholds had been sitting
in the config unused since they were configured. So holo now writes
`holo_rmsd_apo_holo` (apo vs holo binder CA, which is why `_refold` keeps apo's
structure) and checks it against `threshold_rmsd_apo_holo`, alongside
`holo_iptm` against `threshold_ipTM`. Each check is recorded beside its verdict,
and **a missing measurement fails closed** -- the next stage is the most
expensive in the pipeline.

**`uses_kit` on `ModelCapabilities`**, required rather than defaulted so a new
row must say which it is. Before it, `_FoldingBase` applied the kit's rules to
every model: the GPU had to appear in `GPU_TO_CARD`, which ruled out cards the
fork runs on perfectly well, and `n_gpu_shard` was accepted while reaching
nothing. Now the card requirement is kit-only and `n_gpu_shard != 1` is
*refused* for a directly-called model rather than silently ignored -- the same
principle as rejecting a refolding model that cannot read MSAs.

**Two ligand builders, not one.** `_af3_ligand_entries` differs from
`_ligand_entries` in shape *and* in constraint, and the constraint is why they
are separate functions rather than one with a flag. ESMFold2 represents a single
ligand component, so its builder raises on more than one configured residue; AF3
has no such limit. Reusing ESMFold2's would have imposed another model's
restriction and refused a campaign folding the whole chain-E triad that this
stage can handle.

**Metrics across all seeds, not just the best.** `cv_iptm_mean/best/worst` and
the same for `ptm` and `ranking_score`, because a single best score cannot
distinguish a model that is confident from one that is confident once in five --
and that distinction is the entire point of the stage. The headline number is
`cv_rmsd_to_holo`, computed on the best-ranked seed: agreement is corroboration,
disagreement says holo's interface was one model's opinion.

Only the best seed's structure is kept. Five CIFs per sequence across a campaign
is a lot of volume for a comparison already reduced to one number.

## Both new stages, run for real

Holo was re-run to produce the new gate columns, then cross-validation on its
survivors. **The holo gate discriminates, and it is the RMSD check doing the
work, not ipTM:**

| seq_id | holo ipTM | apo/holo RMSD | holo_pass |
|---|---|---|---|
| rgd_core_0_model_1_seq1 | 0.907 | 0.74 | **True** |
| rgd_core_0_model_1_seq2 | 0.799 | 0.64 | **True** |
| rgd_core_0_model_2_seq1 | 0.735 | **6.44** | False |
| rgd_core_0_model_2_seq2 | 0.887 | **5.54** | False |

All four clear `threshold_ipTM` 0.3 by a wide margin -- so on this evidence that
threshold is not where the discrimination lives -- while two exceed
`threshold_rmsd_apo_holo` 4.0. Both of `model_2`'s sequences change
conformation on binding, which means their strong ipTM describes a shape the
apo gate never vetted. Worth noting the gate caught exactly the case it was
written for, and that a campaign without it would have cross-validated two
designs on a false premise.

Then cross-validation, dispatched through `orchestrate`'s own path
(`exit 0`, `stage_reached: cv`):

| seq_id | CV ipTM | holo ipTM | `cv_rmsd_to_holo` | CV pLDDT |
|---|---|---|---|---|
| rgd_core_0_model_1_seq1 | 0.69 | 0.907 | 1.98 | 79.4 |
| rgd_core_0_model_1_seq2 | 0.61 | 0.799 | 0.75 | 75.2 |

The two numbers say different things and both are the point. **On placement the
models agree** -- sub-2 A, and 0.75 A for the second -- so OpenFold3 puts the
binder where ESMFold2 did. **On confidence they do not**: CV's ipTM is 0.19-0.22
below holo's in both cases. That is the shape of result cross-validation exists
to produce, and it is an argument for ranking on agreement rather than on
either model's ipTM alone.

One seed each here, because `--dry-run` forces `num_seeds: 1`; the five-seed
spread was exercised in the probe, where ranking_score ran 0.662-0.733 across
seeds on a single sequence. That spread is roughly the same size as the
CV-to-holo ipTM gap above, which is a caution worth carrying into calibration:
**with one seed, seed variance and model disagreement are not distinguishable.**

## The summary described two stages out of six

Caught by the user reading `summary.json` after the first full run, not by a
test. It held `rfd3` and `backbone_filters` and nothing else, because
`reduce_summaries` passed exactly one entry in `stage_gates` and
`build_summary_json` builds `steps` from that mapping. Everything downstream of
the filters was simply absent.

Fixing it surfaced three more problems, each of which had been producing
plausible numbers rather than failing.

**A gate not declared in `gates.py` is a gate the funnel cannot see.** The holo
gate was written by comparing thresholds directly in `app.py`. It produced
correct `holo_pass` verdicts, so it looked finished -- but it named its columns
`holo_pass_iptm` where `_funnel` counts `{prefix}{metric}_pass`, so every
per-metric failure count would have read **zero** while two sequences were in
fact failing. And the thresholds then existed in two places, which is precisely
what that module's docstring says it exists to prevent. Now declared as
`refold_gates` beside `backbone_gates` and applied through `evaluate_gates`,
which names the columns, collects every failure rather than stopping at the
first, and yields `fail_reasons` for free.

One wrinkle: `evaluate_gates` raises on a metric it cannot find, deliberately,
since within a stage a missing gated value is a bug. Holo's `rmsd_apo_holo` is
legitimately absent when apo left no structure, which is data, not a bug -- so
that case is settled before gating, and settled as a failure. Unknown fails
closed; the next stage is the most expensive in the pipeline.

**`n_in` was right only while one stage was gated.** `_funnel` selected
`stage_reached == stage`, and `stage_reached` records the *furthest* stage
reached -- so equality counts only what stopped there. Correct for a terminal
stage, and `backbone_filters` was the only gated stage until yesterday. The
moment apo had survivors, apo would have reported `n_in: 0`. Latent for months,
wrong the instant a sixth stage existed.

**Two units share one funnel.** `rfd3` and `backbone_filters` count designs;
`mpnn` onward count sequences. Counting rows for a design-unit stage reported
five backbones entering the filters when three designs did -- the same
double-counting `latest_records` already fixes for the CSV, reappearing in the
JSON because sequence rows carry `bb_*` columns forward. Each step now names
its `unit`.

And cross-validation reported `n_fail: 2` when it has no gates at all, which
reads as "two designs failed cross-validation". Nothing runs after it, so
nothing can fail it; it reports `n_reported` instead.

### `requested`, which the user asked for and the records cannot supply

`n_batches` and the sequence fan-out are not recoverable from the output: three
designs could mean "three were configured" or "the rest failed", and at dry-run
scale those are indistinguishable. So the summary now carries what the campaign
asked for beside what it got -- `n_batches`, `diffusion_batch_size`,
`designs_per_spec`, `total_designs`, `n_mpnn_seqs_per_design`, `max_sequences`
(the product, the ceiling if nothing were filtered) and `n_cv_seeds`.

The funnel now reads straight through:

```
rfd3              designs    1 spec -> 3
backbone_filters  designs    3 in, 2 pass, 1 fail   (loop_fraction)
mpnn              sequences  2 designs -> 4
apo               sequences  4 in, 4 pass
holo              sequences  4 in, 2 pass, 2 fail   (rmsd_apo_holo <= 4)
cv                sequences  2 in, 2 reported
```

Which is the first artifact that says, on its own, what the campaign did.
