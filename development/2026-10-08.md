## Six attempts, five causes

Worth recording because only one was the kit's, and the pattern was one bug
hiding behind another.

| # | Died at | Cause | Whose |
|---|---|---|---|
| 1 | step 12 | CRLF from Windows `core.autocrlf=true` | mine |
| 2 | step 11 | OOM, exit 137 -- the kit's `MemAvailable / 9` job heuristic | kit's |
| 3 | step 13 | Modal rejecting Docker's optional `.ta[r]` COPY glob | Modal's |
| 4 | step 11 | Modal builder preemption, "external shut-down" | infra |
| 5 | -- | cancelled by the user | -- |
| 6 | -- | **succeeded** | -- |

**The CRLF one is worth internalising.** `git` on Windows rewrote LF to CRLF,
`from_dockerfile` uploaded that into a Linux image, and the build died on
`run.sh: line 19: set: pipefail: invalid option name` -- which names bash, not
git. Files that are *sourced* would have been worse: a `configs/*.env` with CRLF
sets every variable with a trailing `\r` and surfaces later as an unexplained
`exit 3`.

**The OOM was not reproducible, which was the trap.** The kit computes
`JFA = MemAvailable / 9` for flash-attn, assuming ~9 GB per compile job. 17 jobs
completed on a builder reporting 328 GB and were killed on one reporting 203 GB,
so the real peak is above ~12 GB. Modal hands out whichever builder is free, so
the default makes success a coin flip. Pinned `BUILD_JOBS=8`.

**Capping the jobs made it faster, not slower**, which was the opposite of the
prediction: flash-attn took 1543 s at 8 jobs against 1932 s at 17. Less memory
pressure beat more parallelism.

## Why this kit is so much heavier than boltz2

The user got the boltz2 kit working quickly and reasonably asked why this one
fought back. The kits are not comparable:

| | boltz2 | esmfold2 |
|---|---|---|
| Dockerfile | 58 lines | 130 lines |
| from-source CUDA refs | 0 | 27 |
| `STACK` / `WHEELS_FROM` args | none | both |
| ships a prebuilt wheel | yes, `boltz-2.2.1-py3-none-any.whl` | no, only a `.keep` |

boltz2 is pip-only. esmfold2 compiles **xformers, TransformerEngine and
flash-attn from source** because it pins torch 2.13.0 + CUDA 13.0, for which no
wheels are published -- its own `requirements.lock` says these are "wheels that
exist on no index". ~38 minutes is the floor, not a symptom.

### The wheels cannot simply be banked

Reasonable-sounding plan, and it does not work as stated. `WHEELS_FROM=prebuilt`
verifies each wheel's sha256 against `stock/PINS.json`, and wheel builds are not
byte-reproducible, so our own builds are rejected by the check that path depends
on:

```
flash_attn    PINS.json 81eee74f74d25be1   ours f7702ec5078c3d85   False
xformers      PINS.json 2ed4c2bd0a3dd092   ours cbe915e89cbcf9b0   False
transformer_engine  PINS fe567267d7993574  ours e1a4889a89ecfcb6   False
```

Patching `PINS.json` would fix that, and it is **deliberately not done**:
`stock/PINS.json` and `stock/wheels/` both live under `esmfold2/`, copied at
Dockerfile line 81, *before* the wheel build at line 83. Editing either
invalidates the cache and forces the same 32-minute rebuild it is meant to
avoid -- paying the cost to install the saving. Do it only when a rebuild is
already forced for another reason, e.g. bumping the kit commit.

The wheels are parked at `~/esm_wheels/` (outside the build context, so they
cannot dirty it) and on the weights volume under `esmfold2-wheels/` as
insurance.

**The runtime pin check is a different mechanism and it passes.**
`check_pins.py` validates by *version string*, not by wheel hash, and reports
all three as `pinned (stock/PINS.json "image" layer)`. By the kit's own verdict
we are on-pin; we are running equivalent-by-construction builds of their pinned
sources rather than their exact binaries.

## What the kit actually reports

`check` -- the dry run, no model loaded:

```
DRY-RUN mode=fast variant=full_nomsa server_mode=opt14_msa
  gpu=NVIDIA A100-SXM4-40GB(sm80) n_gpu=1 target_gpu=A100
  levers=fused,t3,t5,t10,tx,ax,af,fz,tg,sg,eg,ec,fc,pb,msa,ls,... (31 on)
  not_for_variant=rg,mh  not_for_class=t16  kernel_key=8.0|3.7
WEIGHTS pinned sha256: 14 files for full_nomsa, 24.9 GiB digested in 98.7 s
```

- `fast` engages on A100 with 31 levers. `not_for_class=t16` is the
  compute-capability-9.0 transition kernel standing down on sm80, exactly as the
  README says; `not_for_variant=rg,mh` are levers irrelevant to this variant.
  Both informational -- neither is `exit 3`.
- The README's "≈24 GiB" is **per variant**, not the whole download: 14 of the
  52 files serve `full_nomsa`; the rest are ESMC-6B and ESMFold2-Fast.
- **98.7 s to digest 24.9 GiB off a Modal volume**, against "a minute or two" on
  local disk. Volume storage costs nothing meaningful here, which matters
  because it would otherwise be paid per container.

### `server_mode=opt14_msa` is not a contradiction

It looks alarming next to `full_nomsa`. It is the internal name of `fast` mode's
kernel composition -- `FAST_LINE = KitMode("opt14_msa", {})` at
`opt/esmfold2_opt/modes.py:135`, a constant for `--mode fast` regardless of
variant (`big` reports the same name with different graph-capture overrides).
The `msa` refers to the fused MSA-module kernel being in that composition, which
is legitimate for `full_nomsa`: ESMFold2 still *has* an MSA module, and the
variant feeds it the query sequence alone at depth 1.

## The apo fold

One real MPNN sequence from the dry-run shards, `--variant full_nomsa`, binder
alone with `"msa": null`:

```json
{"complex_id": "rgd_core_0_model_0_seq1", "variant": "full", "seed": 0,
 "status": "ok", "ptm": 0.4738, "iptm": 0.0, "n_tokens": 102,
 "msa_depths": [0], "wall_s": 54.693, "mode": "opt14_msa"}
```

Produced `cif_all/<seq_id>__full__s0_x0.cif`, a matching `_pae.npz`, and an
appended `pred_rows.jsonl`.

- **`msa_depths: [0]` is proof, not inference**, that no MSA was used.
- **`iptm: 0.0` is correct for a monomer** -- ipTM scores an interface and apo
  has none. It becomes meaningful at holo.
- Setting the input JSON's `id` to `seq_id` makes outputs directly addressable.
- `pred_rows.jsonl` is a convenient source for `apo_*` columns.

### Cost, and the number not to misread

**`wall_s: 54.7` is the fold; the 233.8 s the stage took is dominated by
one-time startup** -- checkpoint load, CCD dictionary, CUDA graph capture,
kernel install. So marginal cost is ~55 s per sequence, not ~234 s.

At 640 sequences that is ~9.8 GPU-hours serial, or roughly 2.5 hours wall-clock
at `max_concurrent: 4`, plus startup amortised across `chunk_size: 24`. Measured
on a 102-residue monomer at `num_diffusion_samples=1`; **holo folds 524 residues
with targets and is a different cost class** -- do not extrapolate.

## Open questions

Carried forward: splitting the chain-E metals, sampler A/B, boltz2's
unverified capability row, the MN NaN-coordinate question, untested gate
thresholds.

New:

1. **The driver margin is 0.95.** Modal's fleet is at 580.95.05 and the kit
   requires `>= 580`. A fleet rollback below that breaks every mode with
   `exit 3`, and there is no fallback -- `ESMFOLD2_OPT_REQUIRE_FAST_ENV` means
   even `--mode off` refuses without flash-attention and TransformerEngine.
2. **Should a refolding model without `consumes_msa` be rejected rather than
   warned?** The user said the refolding model "needs to be a model that
   supports MSA"; `resolve_campaign` currently only warns. Unchanged, because it
   is a deliberate behaviour change to tested code.
3. **The `af3_jax` weights licensing call** -- the kit ships OpenFold3 ported
   weights; official AF3 weights are non-commercial. Bio-Techne legal, not
   engineering. Does not block apo.

## Next

**`run_refold` in `app.py`**, apo first. One Modal function parameterised by
stage, since apo and holo share `refolding.model`; `with_options` supplies the
per-stage GPU. Cross-validation needs its own function because
`cross_validation.model` is `af3_jax` against refolding's `esmfold2` and

dict keyed by `FoldingModel`, the pattern `MPNN_MODELS` already uses.

`esmfold2`, which is `consumes_msa: True`, so holo needs target MSAs -- and
