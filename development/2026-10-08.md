## Six attempts, five causes

Worth recording because only one was the kit's, and the pattern was one bug
hiding behind another.

| # | Died at | Cause | Whose |
|---|---|---|---|
| 1 | step 12 | CRLF from Windows `core.autocrlf=true` | mine |
| 2 | step 11 | OOM, exit 137 -- the kit's `MemAvailable / 9` job heuristic | kit's |
| 3 | step 13 | Modal rejecting Docker's optional `.ta[r]` COPY glob | Modal's |
| 4 | step 11 | Modal builder preemption, "external shut-down" | infra |
| 5 | -- | cancelled by the user | -- |
| 6 | -- | **succeeded** | -- |

**The CRLF one is worth internalising.** `git` on Windows rewrote LF to CRLF,
`from_dockerfile` uploaded that into a Linux image, and the build died on
`run.sh: line 19: set: pipefail: invalid option name` -- which names bash, not
git. Files that are *sourced* would have been worse: a `configs/*.env` with CRLF
sets every variable with a trailing `\r` and surfaces later as an unexplained
`exit 3`.

**The OOM was not reproducible, which was the trap.** The kit computes
`JFA = MemAvailable / 9` for flash-attn, assuming ~9 GB per compile job. 17 jobs
completed on a builder reporting 328 GB and were killed on one reporting 203 GB,
so the real peak is above ~12 GB. Modal hands out whichever builder is free, so
the default makes success a coin flip. Pinned `BUILD_JOBS=8`.

**Capping the jobs made it faster, not slower**, which was the opposite of the
prediction: flash-attn took 1543 s at 8 jobs against 1932 s at 17. Less memory
pressure beat more parallelism.

## Why this kit is so much heavier than boltz2

The user got the boltz2 kit working quickly and reasonably asked why this one
fought back. The kits are not comparable:

| | boltz2 | esmfold2 |
|---|---|---|
| Dockerfile | 58 lines | 130 lines |
| from-source CUDA refs | 0 | 27 |
| `STACK` / `WHEELS_FROM` args | none | both |
| ships a prebuilt wheel | yes, `boltz-2.2.1-py3-none-any.whl` | no, only a `.keep` |

boltz2 is pip-only. esmfold2 compiles **xformers, TransformerEngine and
flash-attn from source** because it pins torch 2.13.0 + CUDA 13.0, for which no
wheels are published -- its own `requirements.lock` says these are "wheels that
exist on no index". ~38 minutes is the floor, not a symptom.

### The wheels cannot simply be banked

Reasonable-sounding plan, and it does not work as stated. `WHEELS_FROM=prebuilt`
verifies each wheel's sha256 against `stock/PINS.json`, and wheel builds are not
byte-reproducible, so our own builds are rejected by the check that path depends
on:

```
flash_attn    PINS.json 81eee74f74d25be1   ours f7702ec5078c3d85   False
xformers      PINS.json 2ed4c2bd0a3dd092   ours cbe915e89cbcf9b0   False
transformer_engine  PINS fe567267d7993574  ours e1a4889a89ecfcb6   False
```

Patching `PINS.json` would fix that, and it is **deliberately not done**:
`stock/PINS.json` and `stock/wheels/` both live under `esmfold2/`, copied at
Dockerfile line 81, *before* the wheel build at line 83. Editing either
invalidates the cache and forces the same 32-minute rebuild it is meant to
avoid -- paying the cost to install the saving. Do it only when a rebuild is
already forced for another reason, e.g. bumping the kit commit.

The wheels are parked at `~/esm_wheels/` (outside the build context, so they
cannot dirty it) and on the weights volume under `esmfold2-wheels/` as
insurance.

**The runtime pin check is a different mechanism and it passes.**
`check_pins.py` validates by *version string*, not by wheel hash, and reports
all three as `pinned (stock/PINS.json "image" layer)`. By the kit's own verdict
we are on-pin; we are running equivalent-by-construction builds of their pinned
sources rather than their exact binaries.

```
  gpu=NVIDIA A100-SXM4-40GB(sm80) n_gpu=1 target_gpu=A100

```

- `fast` engages on A100 with 31 levers. `not_for_class=t16` is the
  compute-capability-9.0 transition kernel standing down on sm80, exactly as the
  README says; `not_for_variant=rg,mh` are levers irrelevant to this variant.
  Both informational -- neither is `exit 3`.
- The README's "≈24 GiB" is **per variant**, not the whole download: 14 of the

- **98.7 s to digest 24.9 GiB off a Modal volume**, against "a minute or two" on
  local disk. Volume storage costs nothing meaningful here, which matters
  because it would otherwise be paid per container.

### `server_mode=opt14_msa` is not a contradiction

It looks alarming next to `full_nomsa`. It is the internal name of `fast` mode's
kernel composition -- `FAST_LINE = KitMode("opt14_msa", {})` at
`opt/esmfold2_opt/modes.py:135`, a constant for `--mode fast` regardless of
variant (`big` reports the same name with different graph-capture overrides).
The `msa` refers to the fused MSA-module kernel being in that composition, which
is legitimate for `full_nomsa`: ESMFold2 still *has* an MSA module, and the
variant feeds it the query sequence alone at depth 1.

Produced `cif_all/<seq_id>__full__s0_x0.cif`, a matching `_pae.npz`, and an
appended `pred_rows.jsonl`.

- **`msa_depths: [0]` is proof, not inference**, that no MSA was used.
- **`iptm: 0.0` is correct for a monomer** -- ipTM scores an interface and apo

### Cost, and the number not to misread

**`wall_s: 54.7` is the fold; the 233.8 s the stage took is dominated by
one-time startup** -- checkpoint load, CCD dictionary, CUDA graph capture,
kernel install. So marginal cost is ~55 s per sequence, not ~234 s.

At 640 sequences that is ~9.8 GPU-hours serial, or roughly 2.5 hours wall-clock
at `max_concurrent: 4`, plus startup amortised across `chunk_size: 24`. Measured
on a 102-residue monomer at `num_diffusion_samples=1`; **holo folds 524 residues
with targets and is a different cost class** -- do not extrapolate.

## `run_refold`, and apo in the pipeline

One Modal function parameterised by stage, because **a function's image is
fixed at decoration time** and `with_options` can override cpu/memory/gpu but
not the image. So `_refold` holds the logic once, `refold_esmfold2` is a
three-line wrapper on the kit image, and `REFOLD_FUNCTIONS["esmfold2"]` is the
lookup `orchestrate` uses. Adding a model is an image, a wrapper and a dict
entry; only models a campaign uses should be declared, since every image in
`app.py` is built on the next `modal run`.

Apo and holo share the function because both read `refolding.model`.
Cross-validation cannot: `cross_validation.model` is `af3_jax` against
refolding's `esmfold2`. That is now **enforced rather than assumed** -- a
validator rejects `cross_validation.model == refolding.model`, because the same
model on both sides is not cross-anything: it would run a second full folding
pass and report a model agreeing with itself, with no error and ranks that read
as corroboration.

`REFOLD_STAGES` is `{"apo": (False, False), "holo": (True, True)}` --
`(include_targets, supplies_msa)` -- and the variant follows from the second
flag via `folding_variant`, so no field can contradict the stage's MSA policy.
Exit 3 raises rather than being returned: a mode that cannot engage is a
configuration error, not a failed fold.

### Three bugs, all silent, all in new code

**1. `b_factor` is not read by default.** pLDDT lives there, and biotite omits
it unless `extra_fields` asks. The first run returned
`apo_plddt_error: AttributeError: 'AtomArray' object has no attribute
'b_factor'`. Fixed by threading `extra_fields` through `load_structure`, both
branches. The per-metric guards meant this cost one column rather than the
chunk -- the design working as intended under a real failure rather than in
theory.

**2. The MPNN phase was ungated.** `--start-at apo` re-ran it. Latent while
MPNN was the final stage and correct then; a real bug the moment apo existed
beyond it. Harmless at dry-run scale because MPNN is deterministic under a fixed
seed, but a wasted GPU pass over every passing design at campaign scale, and it
defeats the point of starting late.

**3. A stage inherited its own stale columns.** The apo re-run that fixed pLDDT
still carried the previous attempt's `apo_plddt_error`, so one row asserted both
a value and a failure. `REFOLD_SUPERSEDES` now drops a stage's own prefix plus
every downstream one, while keeping apo's columns when holo runs, since the
apo/holo gate needs them.

344 tests, 13 new: the contradictory-error shape specifically, that upstream
`bb_*`/`mpnn_*` columns survive a refold, that holo keeps apo, that every stage
in `REFOLD_STAGES` has a `REFOLD_SUPERSEDES` entry, and the cross-validation
model rule. That last set also surfaced a pre-existing validator -- `variant`
and `weights` are only accepted for `af3_jax` -- which had made the first
version of the test fail for an unrelated reason.

## Which stage the MSA egress trap actually belongs to

A correction worth recording, because the notes had it filed under the wrong
stage and that section exists to prevent exactly this.

**The ESMFold2 kit contacts no MSA server.** No `use_msa_server`, `msa_server`,
ColabFold or MMseqs reference anywhere in its Python, shell or docs. It reads an
a3m handed to it, or folds without one.

So `--use_msa_server` and everything around it -- the non-caching behaviour,
the two independent suppression gates, the `len > 1` pairing threshold, the
early return that discards paired results -- are **AF3-fork** mechanics and
apply to **cross-validation**, whose model is `af3_jax`. Holo on `esmfold2` has
no automatic egress to disarm at all. That makes holo materially closer than
previously thought: the remaining work is building target a3m files, and the
only sequences that leave are the targets, which for this campaign are public
proteins. The binder never needs an alignment here, so the sensitive sequences
stay in-house by construction rather than by suppression.

### MSA capability flags

Added to `MODEL_CAPABILITIES`, because "does this model want the pairing done
for it" was a fact living only in conversation:

| model | unpaired | paired | -> consumes_msa |
|---|---|---|---|
| `esmfold2` | yes | **no** | yes |
| `esmfold2-fast` | no | no | no |
| `boltz2` | yes | **no** *[unverified]* | yes |
| `af3_jax` | yes | **yes** | yes |

Two booleans rather than one enum, on the user's suggestion and it is the better
shape: the question at assembly time is per-field ("emit an unpaired one? a
paired one?"), and a campaign can ask whether *any* of its models needs paired
alignments without pattern-matching an enum.

The user then spotted that **`consumes_msa` becomes redundant** -- it is
`msa_unpaired or msa_paired`. It is now a derived property rather than a stored
field, which removes the state where it could contradict the flags and
eliminated two of the three consistency rules originally planned. The one left
is `msa_paired` implies `msa_unpaired`, checked in `__post_init__`: pairing
refines per-chain alignments rather than replacing them. Blast radius was nil,
since `config.py` already exposed `consumes_msa` as a delegating property.

**boltz2's `msa_paired=False` is unverified, with an asymmetry worth naming.**
For `supports_templates`, `False` prevents a campaign silently requesting
something that would be dropped. For `msa_paired`, `False` risks silently
*under*-supplying -- if boltz2 does want paired alignments we would never build
them, and predictions would be quietly weaker rather than refused. The same
conservative-looking value fails in the opposite direction, so the reasoning
does not carry over by proximity.

### The input schema, read properly this time

The kit documents it at `opt/esmfold2_opt/inputs.py:7-9`. The example file
`w4_public_slice.json` contains protein chains only, which is what led to the
assumption that protein was all there was:

```json
"sequences": [
  {"type": "protein", "id": "A", "sequence": "...", "msa": null},
  {"type": "protein", "id": "B", "sequence": "...", "msa": "msas/B.a3m"},
  {"type": "ligand",  "id": "L1", "ccd": ["ATP"]}
]
```

Four types, `protein|rna|dna|ligand` (`inputs.py:62`). Non-ligand chains need a
`sequence`; ligands take `ccd` or `smiles` (`inputs.py:63`). And `msa` is the
*kit's* extension rather than upstream's field (`inputs.py:8`).

**So ESMFold2 does take ligands, and holo as written omitted one** -- it folded
binder plus protein targets, missing the metal RFD3 designed around and that
`bb_ligand_clashes` / `bb_ligand_min_distance` already measure. Now derived
rather than named in code, which the input structure argues for forcefully:

```
chain D  res 1004        MN
chain E  res 703,704,705  MN
rfd3.ligand: "E703"  ->  {"type": "ligand", "id": "E", "ccd": ["MN"]}
```

The user's first instinct was that the ligand should be "the chain after all the
protein chains". That would be **D** -- a different ion the campaign does not
use, at residue 1004, nowhere near E's numbering. Neither the letter nor the
residue id is guessable, and the letter has to match RFD3's output anyway since
the structural comparisons pair on `(chain, res_id)`. So it comes from
`rfd3.ligand` plus a lookup in the structure, and a named position absent from
the structure raises rather than silently emitting nothing. That check proved
itself immediately: a test guessing `D701` got the error instead of a bogus
entry.

**ESMFold2 takes one ligand component, not a chain of them** (the user's
knowledge; my first implementation emitted `["MN","MN","MN"]` for the triad,
which was wrong). More than one configured residue now raises rather than
folding against a subset, which would score the binder on a complex it was not
designed for.

That check sits in `_refold` rather than the schema, deliberately: RFD3 can
legitimately be given the whole triad, so such a campaign validates and runs
through RFD3 and MPNN before failing at holo. A late failure, and agreed as the
user's to manage -- whoever splits the metals for RFD3 needs to know holo cannot
fold them.

## The full pipeline, and RFD3's seed

### Five stages, one command

A full dry run now goes rfd3 -> backbone_filters -> mpnn -> apo -> holo ->
reduce. Two config changes made it reachable:

**`threshold_plddt_binder: 40.0` in `DRY_RUN_OVERRIDES`.** At smoke scale the
production value of 70 rejected every sequence, so holo folded nothing and the
phase announced `SKIPPED -- 0 of 6 sequences passed apo`. A dry run exists to
exercise the pipeline's shape, and a gate that stops it two stages short defeats
that -- while lowering the real threshold to make a smoke test pass would have
been the wrong fix. A test pins that *only* this gate is relaxed:
`threshold_ipTM`, `threshold_rmsd_apo_holo` and `threshold_rmsd_motif` keep
their production values, so `DRY_RUN_OVERRIDES` cannot quietly become "turn off
the gates".

**`refolding.gpu: A100-40GB`**, down from 80GB, now that holo is known to fit at
522 tokens. `cross_validation.gpu` stays at 80GB -- `af3_jax` is hungrier.

The first full run, six sequences from three designs:

discards candidates that look good in the complex. Worth weighing before the
production threshold is trusted -- and only visible once both stages run.

### RFD3 was sampling unseeded

Two runs of a byte-identical campaign produced different backbones. `run_rfd3`
passed no seed at all, and RFD3's default is `seed: None`, so this was upstream
behaviour rather than an omission in config -- but it meant a campaign could not
be repeated, and a sampler comparison could not be attributed.

**Finding the key took two wrong turns, both instructive.** `seed: null` is
written in `configs/inference_engine/base.yaml`, so the obvious override was
`inference_engine.seed=0`. RFD3 refused it:

```
ConfigCompositionException: Could not override 'inference_engine.seed'.
To append to your config use +inference_engine.seed=0
```

That broke the dry run outright -- `exit 1, 0 designs`. And **Hydra's suggested
fix would have been worse than the error**: `+inference_engine.seed=0` appends a
key nothing reads, so sampling would have stayed unseeded while the config
looked set. Taking the suggestion would have manufactured exactly the
silent-wrong-answer failure this pipeline keeps producing.

The answer came from composing the config the way `rfd3/cli.py` does rather
than grepping the tree: `inference.yaml` selects `inference_engine:
rfdiffusion3`, which is `@package _global_` inheriting `base`, so the key merges
at the **root**. The override is plain `seed=0`, beside `out_dir` and
`n_batches` -- keys the pipeline already passes. The lesson is that where a key
is *written* is not where it *ends up*.

### A seed fixes the discrete sampling only

| | binder length | motif offsets |
|---|---|---|
| unseeded | 118 | A17, A46, A63 |
| seeded A | 108 | A70, A89 |
| seeded B | 108 | A70, A89 |

The seed is genuinely effective -- both seeded runs chose the same length and the
same motif placements, where the unseeded run differed in both. But the
diffusion trajectory diverged: `bb_rg` 12.63 against 12.40, `bb_loop_fraction`
0.295 against 0.324, and all four MPNN sequences entirely different, because
MPNN was designing against a different backbone rather than being unseeded
itself.

**Two corrections to claims made during the investigation.** First, "4 A drift
cannot be CUDA noise" was wrong -- over `num_timesteps: 200`, non-deterministic
reductions amplify chaotically, and the evidence says that is what happened.
Second, reporting `SAME DESIGN SET: True` overstated things: `seq_id` is
positional, so matching names proved nothing about the backbones. The `bb_*`
columns were the real test and they showed the geometry differing.

Accepted on the user's call: chasing bit-exactness would mean forcing
deterministic algorithms inside RFD3, which this pipeline does not control and
which costs speed. The practical consequence is that a dry run reproduces in
*shape* but not in numbers, so the queued sampler A/B should compare
distributions over several designs rather than diffing two runs.

`Rfd3Config.seed` therefore defaults to None, with `apply_dry_run` setting it
from `general.base_seed` -- reproducible smoke tests, diverse backbones at full
scale, and a campaign that pins its own seed keeps it.

## Next

**The af3_jax probe**, for cross-validation. Cheaper than ESMFold2's: its
Dockerfile has no from-source CUDA extensions and its weights are 2.3 GB rather
than 55 GB. Three things to settle first:

1. **One `~/ubm` holding both kits, isolated by `ignore`.** `context_dir` must
   be the parent of `common/opt_core`, so it cannot be narrowed per kit, and
   Modal appears to hash the whole context -- adding `_jitcache/` changed the
   esmfold2 image id and cost a rebuild. `from_dockerfile(ignore=[...])` should
   keep each kit's context stable. Verify by adding `ignore=["af3_jax", ...]`
   to the esmfold2 image *before* af3 is checked out: the post-ignore file set
   is then unchanged, so if the hash is computed after ignoring, nothing
   rebuilds. If it does rebuild, fall back to separate checkouts.
2. **`af3_native` is approved but not known to work.** The kit is built around
   the ported `p2` checkpoint -- `AF3_JAX_PARAMS_ROOT` holds
   `p2/of3_ported_weights.bin.zst` and `install` fetches and converts that
   file -- so native weights may need a separate route rather than a config
   flip. The probe should report what `install` actually lands.
3. **`af3_jax` is the only model with `msa_paired=True`**, so cross-validation
   needs paired alignments, which the cache deliberately does not build. This
   is where the `fill_missing_msas` mechanics in `Notes.md` section 9 stop being
   theoretical, and where the user's decision that binder sequences may appear
   in a paired query applies.

**`threshold_plddt_binder: 70` is settled** -- the user has used that value
before, and apo rejecting binders that holo scores above it is the intent rather
than a miscalibration: a binder should fold correctly on its own, not only when
the target holds it in place. That is what makes apo worth running as a filter
at all.

**A refolding model without `consumes_msa` is now rejected**, not warned
(settled 2026-10-08). The user's reasoning: naming a refolding model means

Also open: the apo/holo gates (`threshold_rmsd_apo_holo`, `threshold_ipTM`),
which now have data to act on. `_refold` already
assembles the target chains but sets their `msa` to `None` as a placeholder, so
running holo now would fold targets without alignments. `Notes.md` section 9 is
the thing to read first: `--use_msa_server` does not cache despite its help
text, and would POST every designed binder sequence to api.colabfold.com.

Cache the **unpaired** MSAs only -- an unpaired MSA is a property of one
sequence and so cacheable, while a paired MSA is a property of the set of chains
queried together. One campaign-specific exception worth exploiting: because the
binder is always suppressed, the pairing context is exactly the target set,
which does not change across a campaign, so the targets' paired MSA could also
be computed once.
