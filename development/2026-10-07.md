## Two wasted launches, and what they actually were

Neither was a bug in the pipeline. Both cost a GPU launch and, worse, pointed
diagnosis at imaginary problems in `_spec_of` and the spec readers.

**A bare `RemoteError` from `orchestrate.remote` means the app was stopped.**
The Rich traceback shows only the client call stack, so it reads like a remote
crash. The actual cause is in the *head* of the log, not the tail:

```
Stopping app - user stopped from dashboard.    (or: from CLI)
Runner terminated.
```

**Redirecting Modal's stdout to a file needs `PYTHONIOENCODING=utf-8`.** The
Modal 1.6.0 CLI prints a check-mark glyph (U+2713) in its banner. With stdout
redirected, Python drops to cp1252 and the run dies on the first line:

```
'charmap' codec can't encode character '\u2713' in position 0
```

Nothing in this repo contains a non-ASCII character -- verified by scanning
every `.py` -- so there is no point hunting the glyph in our own source.

Both are recorded in `Notes.md`, with the launch incantation that avoids them.

## Logs: the pipeline was blind by construction

The dashboard log view was empty for a reason, and the reason was ours, not
Modal's.

1. **`run_rfd3` swallowed everything.** `subprocess.run(..., capture_output=True)`
   held all of RFD3's output in a pipe for the duration and returned only the
   last 2000 characters of stderr *after* the step finished. On a six-hour
   timeout that is total blindness. `populate_weights` had the same shape.
2. **`orchestrate` printed nothing at all.** It built a dict and returned, so
   "it is on the orchestrate step" conveyed no information.
3. **Neither image set `PYTHONUNBUFFERED`**, so even prints that did exist would
   have sat in the buffer.

Replaced with `_stream` (`app.py:77`): prints each line as it arrives, merges
stderr into stdout to preserve the interleaving the subprocess intended, keeps a
bounded 60-line tail for the report, and kills via a `threading.Timer` watchdog
rather than a deadline checked per line -- so a process that hangs *while
printing nothing* still dies. Verified directly: a silent 60 s sleep under a 3 s
timeout was killed at 3.0 s.

The report key changed from `stderr_tail` to `output_tail`. Nothing consumed it.

**The change paid for itself on the next run**, which is the part worth keeping:
the first streamed run immediately produced the real failure below. The old code
had been reporting `returncode: 1` into a dict and carrying on.

## The input path bug

RFD3 exited 1 with zero designs, which surfaced as `phase filter: 0 chunk(s)`:

```
FileNotFoundError: '/data/motif_scaffold_alphav_beta3/alphav_beta3_01-dryrun/
                    rfd3/inputs_motif_scaffold_alphav_beta3/alphav_beta3_fib10_clean.pdb'
```

Note the shape: the run root, then `rfd3/`, then the *campaign-relative* path
glued onto the end.

**RFD3 resolves a relative `input` against the directory holding the specs file,
not the working directory.** `build_rfd3_specs` was emitting `input` as the
campaign-relative path verbatim, while `_prepare` uploads the structure to
`/data/inputs_.../x.pdb`. The two never pointed at the same file.

`ResolvedCampaign.structure_path` looks like the obvious fix and is not usable:
in `_prepare` it is resolved against the *client's* filesystem, so it would
write a `C:\Users\...` path into a file consumed inside a Linux container. So
`build_rfd3_specs` / `dump_rfd3_specs` now take an explicit `input_path`, and
`_prepare` passes the container path. Four regression tests cover it: applied to
every key, survives the YAML dump, accepts a `Path` but emits a plain scalar,
and the no-override default still works for a local run from the repo root.

## The MPNN stage

### Vendoring, and why it was the right call

LigandMPNN cannot run as published here. Its bundled openfold uses three numpy
aliases removed in 1.24 (`np.int` x3, `np.object` x2, `np.bool` x1), which is
why upstream pins `numpy==1.23.5` -- and that pin has no cp312 wheels.

The path I had started down was to honour the pin: a Python 3.11 image of its
own, with the `.cif.gz` -> PDB conversion and the shard writing split into
separate `cpu_image` functions either side, because biotite could not live
beside numpy 1.23.5. Vendoring the tree and fixing six one-word occurrences
collapsed all of that: it runs on 3.12 with **numpy 2.5.3** and current torch,
in one image, sharing the project's own code. A scan found zero numpy-2.0
removals, so those six were the whole barrier.

`requirements.txt` is therefore deliberately not installed. The trimmed tree
keeps only the runtime-essential files; `LOCAL_CHANGES.md` records every
deviation from upstream `26ec57a`, verified by diffing the whole tree.

### Three silent bugs, none of which errored

**1. MPNN redesigned the target chains.** Without `--chains_to_design`, MPNN
designs *every* chain. It invented new sequences for B and C and optimised the
binder against them:

```
native:   QWFGASVRSKQDKILACAPLYHWRTEMKQEREPVGTCFLQDGTKT...
design 1: SMFGSTVVTKGDYTLKTAPLETSGGLDEPGSEPVGRGELTKGDKTV...
```

The output was plausible binder sequences for a target that does not exist. The
giveaway was `num_res=521` -- the whole 524-residue system minus only the three
fixed residues. The probe now asserts the target segments come back
byte-identical to the native, because that is the cheap check.

**2. `--seed 0` was silently discarded.** `run.py` tested `if args.seed:`, falsy
for zero, so an explicit 0 became `np.random.randint(0, 99999)`. Combined with
argparse's `default=0`, the documented default *was* random and seed 0 could not
be requested at all. This campaign sets `general.base_seed: 0`, so sequence
generation was unreproducible while reporting a seed it had invented -- observed
87657. Fixed in the vendored copy to `if args.seed is not None:` with
`default=None`, which keeps upstream's intent that omitting the flag randomises.
Re-running now reports `seed=0`.

**3. The summary double counted backbones.** Carrying each backbone's `bb_*`
columns onto its sequence rows is deliberate -- `summary.csv` is one row per
sequence, so a sequence has to keep its backbone's metrics. But the reducer then
counted the backbone shard alongside its sequences and reported
`n_passing_backbone_filters: 3` for a single passing backbone.

`latest_records` drops a backbone record once sequences exist for that design
and keeps it otherwise, which is exactly the set the plan describes. The shards
are untouched, so `--start-at mpnn` still sees every verdict. The tally now
counts distinct designs rather than rows. 4 rows / 3 passing became 3 / 1.

Also found: `reduce_only` had no `--dry-run`, so it reduced `{run_name}` while
the dry run's shards sat under `{run_name}-dryrun` -- a summary of nothing
rather than an error.

### What the stage does

`run_mpnn` is chunked like `filter_designs`, for a stronger reason: MPNN is
~7.5 s for eight sequences over a 520-residue system, nearly all of it loading
the model, so a container per design would be almost pure startup.
`--pdb_path_multi` and `--fixed_residues_multi` take JSON maps, so one
invocation covers a whole chunk with per-design fixed residues.

Fixed residues are **read from each design's shard**, not re-derived. The
numbering conversion lives in one place because input-vs-output numbering fails
silently, and reading the recorded value also means restarting at `mpnn` selects
the same designs a continuous run would, since `bb_pass` comes from the shards
too.

MPNN's own echo confirmed the semantics: redesigned `A1-A48, A52-A105`, fixed
`A49, A50, A51` plus all of B and C. The binder minus the motif, targets as
context.

Verified from the persisted `summary.csv` rather than from MPNN's log:

```
rgd_core_0_model_0_seq1: seed=0 seq_rec=0.3824 motif@49-51='RGD' len=105
rgd_core_0_model_0_seq2: seed=0 seq_rec=0.3725 motif@49-51='RGD' len=105
rgd_core_0_model_1:      backbone row, bb_pass=False, never reached MPNN
```

### On linking backbones to sequences

Raised as a possible summary addition; **already present twice** and so not
implemented. Every sequence row carries `design_id`, `seq_id` is
`{design_id}_seq{N}`, and `_LEADING` puts them adjacent in the leftmost columns.
Each sequence row also carries its backbone's whole `bb_*` block. A third
representation of the same relation could only drift out of agreement with the
other two.

What was added instead is `mpnn_n_seqs`: not a link, but an invariant. With
`batch_size=8, number_of_batches=1` every design should yield exactly eight, and
a design that quietly yielded five is otherwise visible only by counting rows --
which nobody does at 320 designs.
